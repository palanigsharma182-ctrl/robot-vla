## 要回答的问题

同一个 VLA 在 reach → grasp → lift → transport → place 中，主要受限于：

1. 单个技能的动作能力、几何定位或控制跟踪；
2. 模型自产的上一技能结束状态不满足下一技能的需要；
3. 联合训练的技能覆盖、事件监督或技能间能力折中；
4. 组合执行时的观测、时间对齐、command reference 或累积漂移。

Memory、自动重观察、World Model 和 Critic 暂不作为本批次新增变量。
上一轮小试 checkpoint 不用作五技能主模型：它只见过四个 HOME/pregrasp 样本。

## 固定模型与数据方向

- 单个共享 VLA；冻结 Qwen，沿用已恢复的 Layer12 V1 checkpoint 初始化 Adapter/Expert。
  这是当前可运行基线的 development 实验，不把 Layer12 晋升 canonical 默认层。

- 沿用 Stage1Trainer 的 BF16 AMP、优化器、梯度裁剪、训练状态和 checkpoint 实现。
- 首先使用 D0 的完整五技能 train 轨迹；训练数据包含完整组合语言和跨技能动作窗口。
  原子技能标签用于采样和诊断，不新增模型 skill-id 输入，不拆成五个动作网络。
- D1 局部 DAgger 先只盘点，不混入首个基线，避免在定位前同时改变数据分布。
- 仅使用既有 train split；历史 val/confirmation/final-test 不在本批次重新运行。
  当前训练 CLI 会自动加载旧 val，不能原样直接启动；新实验入口应复用 Trainer、只建 train loader，
  用全新仿真 development 场景评价，明确与历史 selection 协议隔离。
- 完整评估 CLI 的 `--test-episodes` 默认会包含旧 test。若复用此 CLI，冻结命令必须显式设置
  `--test-episodes 0 --unseen-seed-start 1001000 --unseen-episodes 10 --qwen-context-layer 12`。

## 执行顺序与可验收产出

### A. 训练前测量

先评价恢复 checkpoint，不能只看训练后模型。使用相同的新场景和推理设置比较前后。

- 原子技能：五技能各5个场景，从专家验证的前置状态开始，最多100个 policy steps。
- 相邻组合：reach→grasp、grasp→lift、lift→transport、transport→place 各5个场景。
  专家只准备第一个技能的起点；交接时不 reset、不补专家动作、不清空策略正常跨步状态。
  同时记录第一技能通过数、第二技能通过数、条件分母和完整两技能成功数。
- 完整任务：10个场景，从自然初始状态完成五技能，最多400个 policy steps。
  保留未到达的后续技能；条件分母为0时报告不可估计，不能写成该技能成功率0%。
- 原子起点和组合起点需要配对 scene seed 与起点准备语义。相同 seed 不声称轨迹逐动作相同。

拟定 development seed 段：atomic 与 adjacent pairs 共用1001000–1001004，
full-chain 为1001000–1001009。前五个场景跨模式有意配对，唯一评估单元为
`(checkpoint, mode, start_skill, end_skill, scene_seed)`，不把跨模式复用误算为重复独立场景。
执行前核对这批新场景与训练及已有本项目实验 seed ledger 不相交。
这些是 development，不是独立 final test，也不自动支持正式推广结论。

### B. 五技能联合训练

本阶段是用户要求的 development 基线续训和前后对照，不宣称新训练机制。
D024 已有联合训练 plateau/技能折中的历史证据，不能把“增加 steps”本身当作瓶颈解释。
A 若出现接口、控制或数据协议错误，先修复相关工程问题再启动依赖它的训练；若 A 复现

不以此恢复旧 E012 selection，也不自行增加新模型结构或 DAgger 分布。

先以小批次测量吞吐/显存，再在用户批准的累计预算内冻结实际训练规模。
初始建议：micro-batch 1、gradient accumulation 8、均衡五技能采样，完整轨迹和跨边界窗口保留。
沿用正式基础 Flow + 既有事件监督；学习率、warmup、总更新数和保存点在首个 optimizer step 前
统一记录，不依据开发效果随意改动。初步目标为256和1024 optimizer steps两个检查点，
是否能在本批次完成须由吞吐和预算确定，不能把“跑满时间”叫作“已收敛”。

按技能记录实际样本曝光、基础/事件误差和训练曲线；记录完整 trainer/RNG/sampler 恢复身份。
保留初始权重、预定检查点及最后完整恢复点；不只保存事后最好的某个技能 checkpoint。
时间与磁盘上限内为闭环评估和结果回传预留资源，不把全部预算耗在 optimizer steps。

### C. 同协议复测与归因

复用 A 的 development 协议评价预定训练检查点。主报告同时呈现：

| 层级 | 指标 | 能回答的问题 |
|---|---|---|
| 原子技能 | 每技能成功数/总数，位置残差、抓取/释放稳定性 | 技能在合格起点是否会做 |
| 相邻组合 | 第一技能通过数，第二技能条件/无条件完成数 | 自产交接状态是否成为瓶颈 |
| 完整任务 | full success、五技能无条件完成数、mean completed skills | 长链执行主要断在哪里 |
| 控制与系统 | tracking saturation、异常重规划、推理/控制错误、时间上限 | 是否为工程故障掩盖模型能力 |
| 训练 | 各技能曝光、基础/事件 loss、不同检查点的能力变化 | 覆盖不足或技能能力折中是否值得深入 |

原子成功、组合失败支持调查交接分布，但单靠差值不能断言具体原因。
单技能一直失败优先检查数据、目标动作和控制；只在证据指向后再加入 Memory 或其他模块对照。
不因某项技能改善就忽略其他技能退化，也不把历史 E012 未通过 selection 的权重追认为 accepted。
